## Problema 1: o comando anunciado não existe fora do clone

> quando rodo o npm run atualizar -- --aplicar em um container que possui a extensao ou em
> qualquer outro local que não seja este diretorio ocorre isto:
>
> ```
> iagoleal@MacBook-Pro-de-Iago erp-mineracao % npm run atualizar -- --aplicar
> npm error Missing script: "atualizar"
> npm error
> npm error To see a list of scripts, run:
> npm error   npm run
> npm error A complete log of this run can be found in: /Users/iagoleal/.npm/_logs/2026-09-11T19_48_11_766Z-debug-0.log
> ```

O diretório de onde o comando saiu é `erp-mineracao`, outro projeto do usuário, com a extensão
instalada e o painel aberto. O erro é o do npm, não do ritual: `npm run` só enxerga os scripts do
`package.json` do diretório corrente, e `atualizar` está declarado apenas no `package.json` deste
clone (`package.json:70`). Fora dele não há script algum com esse nome, logo o ritual nunca chega a
executar e nenhuma das recusas nomeadas de `scripts/atualizar.js` se pronuncia.

Quem anuncia o comando é a faixa do cabeçalho do painel, pela constante `UPDATE_COMMAND` em
`src/webview/domain/labels.ts:183`, com o valor `npm run atualizar -- --aplicar`, sem qualquer
menção ao lugar de onde rodá-lo. O painel, porém, abre no workspace que o leitor tem aberto, que na
esmagadora maioria das vezes não é este clone. O README também soletra o comando nu, na seção do
ritual, dentro de um documento que pressupõe o leitor no repositório (`README.md:187`).

Este é o defeito registrado como `BUG-20260911-FI3O`.

## Problema 2: a expectativa declarada de atualização de qualquer lugar

Perguntado o que esperava ao rodar o comando fora do clone, o usuário respondeu com o desejo, e não
com o critério:

> Também gostaria que, ao identificar a diferença entre a versão atual e a da origem, ao rodar o
> comando ele baixasse a atualização independentemente de onde eu estiver, seja num container de
> desenvolvimento ou num Codespace, e que a extensão se atualize automaticamente de acordo com o
> repositório.

Há duas coisas distintas aqui, e elas custam diferente.

A primeira, o comando alcançável de qualquer diretório, é a contrapartida direta do problema 1 e
cabe dentro do desenho atual: o ritual continua sendo ato de terminal, e o que muda é a forma de
invocá-lo e o que a faixa anuncia.

A segunda, a extensão atualizar-se sozinha, colide de frente com o invariante mais duro do projeto,
escrito na seção 6 do PRD e reafirmado em cinco adendos: **a extensão nunca escreve arquivo**. O
README declara a ausência de auto-atualização como decisão, não como lacuna (`README.md:143`). Não
registro isso como bug, porque bug é distância entre o comportamento e a spec, e aqui o
comportamento é a spec. Fica anotado como pedido de evolução, a ser tratado pelo ciclo forward, que
é onde uma restrição de PRD pode ser emendada com o registro que ela merece.

Ambiente citado e ainda não caracterizado: container de desenvolvimento e Codespace. Em nenhum dos
dois se sabe, por este relato, se o clone do `reversa-views` existe na máquina onde o painel roda.
A pergunta importa para o conserto e está aberta no bug.

## Problema 3: o painel abre como janela de terminal, e o usuário a quer como aba de editor

> algumas coisas têm me incomodado. Uma delas é que a janela do reverso se abre como o mesmo tipo de
> janela do terminal, o que prejudica a visualização. Gostaria que ela abrisse como um arquivo, igual
> ao funcionamento da extensão do Kanban, e que operasse como se estivesse dentro de um diretório
> ".vsconfig" ou algo nesse sentido.

O que o manifesto declara hoje é uma view de webview num contêiner da barra de atividades
(`package.json`, `contributes.viewsContainers` e `contributes.views`), e é exatamente por isso que o
painel divide o espaço estreito com o terminal. A extensão de Kanban que serve de comparação abre
seu quadro como aba do editor, e é o que o usuário pede.

Também aqui o comportamento observado é o comportamento especificado, e portanto isto não é defeito:
é mudança de superfície, com desenho próprio a fazer. A menção a `.vsconfig` ficou como o usuário
disse; presumo `.vscode`, a pasta de configuração do workspace, mas não confirmei e não interpreto
por conta própria. Anotado para o ciclo forward.
